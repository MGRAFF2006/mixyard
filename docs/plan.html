Shared policy, three native transports

Sources → user-defined mixes → devices + exported virtual inputs

Optional acyclic mix-to-mix routing follows initial native transport proof. Privacy exclusions, destination mix-minus and microphone consent must propagate through every path. A summed mix cannot be unmixed downstream; reject excluded-source paths and rebuild a safe upstream mix. Initially reject duplicate source paths at a destination, and qualify transitive headroom including output gains.

A small Rust policy CLI persists exact source identities, arbitrary mix IDs, sends and output routes. Native code handles audio. Missing or ambiguous sources contribute silence, while other selected sources can continue. Repair touches only Mixyard-owned resources.

“Every OS” cannot promise equal access. Android/iOS public capture APIs do not establish arbitrary virtual microphone injection; companion controls or cooperating apps are possible future paths. Android · ReplayKit

Desktop apps, tray panels and agent-friendly CLI

Desktop app, tray panels and a true headless CLI

Choose Tauri 2 with a shared Vue 3/Vite interface, qualified in the real OS webviews. A separately managed native runtime owns audio. App, tray and CLI share state; closing or crashing the app must leave sound running.

Use private per-user local IPC with peer checks or current-user named-pipe ACLs and reject remote pipe clients. No public control listener. The runtime and CLI build without Tauri or webview dependencies.

Call/Record/Monitor presets and simple selectors are the everyday view. The CLI needs stable JSON, meaningful errors and event output for agents, with no GUI installation required. Windows tray, macOS menu bar and supported Linux panel hosts get quick controls; Linux’s tray menu is the baseline until rich panels are verified.

Performance is a gate, not a toolkit promise: proposed interaction p95 ≤100 ms, responsive dragging/scrolling and no UI-induced audio artifacts. Meter updates are bounded; samples never pass through the webview. A client that cannot meet these gates gets replaced without changing routing. Tauri model · Tray limitations

Audio quality: non-negotiable release gates

Sound quality is a release blocker

  • Delay-aligned unity-path PCM comparison, plus a nonrepeating waveform to catch brief corruption, dropped/repeated samples and leakage. Freeze conversion tolerances beforehand.
  • Two-hour stress run, then an overnight eight-hour run with all buses active: zero detected unexplained artifacts, bounded memory and no growing latency. Missing telemetry means unknown.
  • Measure actual wired monitoring latency by workload. Proposed targets: p95 ≤20 ms, p99 ≤30 ms on qualified setups. Bluetooth is qualified separately.
  • Test gain/mute/startup/recovery transitions for clicks, clipping and unintended routes. Native realtime processing stays clear of disk, blocking work and UI.
Bluetooth quality and supported controls

Bluetooth: audio quality and every supported control

Target play/pause, volume, mic mute and call answer/end. Each device can preserve normal OS behavior, choose a primary routed player, or control all eligible routed players. Hardware mute, mix mute and recording mute remain distinct; call controls need device-and-app qualification.

Do not open a headset mic merely for discovery or idle meters. Show profile/codec changes where known. Classic Bluetooth can reduce playback quality when its mic is active; on Windows even Communications-category playback can trigger that mode. Monitor uses an ordinary media category by default.

High-quality stereo plus headset mic depends on the actual radio, headset, OS and driver. Unsupported or unknown controls/profiles remain visible. Windows profiles · Apple quality behavior · Linux Bluetooth policy

What is buildable, and what still needs proof

Custom logical mixes, multi-device fan-out, shared GUI/CLI state and media target policies are feasible. Dynamic Windows/macOS input publication, real audio reliability and device-origin button interception need native proof. An unchanged fixed-channel virtual cable does not supply arbitrary named microphones.

Export OS inputs only when requested. Report real capacity limits; never silently truncate mixes. One slow or disconnected output must not stall siblings. Independent device clocks need rate matching; sample-synchronous Bluetooth playback is not a universal guarantee.

From prototype to usable release

Evidence required before “working”

  1. Policy and build: validate graph safety and compile native tools. This does not prove audio delivery.
  2. Real transport: an external app records both virtual inputs. Distinct tones prove selected sources, excluded call return, gain/mute and channel mapping.
  3. Recovery: unplug/replug, app relaunch, default changes, producer crash during route mutation and repeat apply. Preserve unrelated routes. Linux recovery tests include WirePlumber.
  4. Usable release: measure clock drift and end-to-end wired monitoring latency; qualify permissions, installers and signed driver distribution. Connect the parallel UI prototype and recording integrations after transport proof.
Independent review: corrections accepted

The reviewer’s in-memory mixing check passed independent gains, mix-minus, private-source exclusion, disabled mic monitoring and missing-mic silence. It proved the model only.

Two counterexamples changed the plan: three aligned 0.5-amplitude sources peak at 1.5; hypothetical 100 ppm clock mismatch grows by 6 ms/min at 48 kHz. We now require explicit headroom/channel rules and clock adaptation tests.

Independent follow-up reviews approved quality gates, UI/runtime separation and the custom mix/control model. Added edge gains, owned rollback, fan-out isolation, corruption checks, device-origin plus dispatch-ownership gates, and retained paused-player associations. No native Windows/macOS test hosts are verified; real audio qualification remains open.

Limits we must keep visible

Stable routing cannot disable a call app’s own AGC, echo cancellation or noise suppression. If the virtual input disappears, the app may choose a physical mic outside our control. Browser media constraints

Automatic recording initially means a stable Record input and supported consumer rules. An owned recorder later needs recoverable segments, gap/disk-full reporting and explicit arming. Software mic monitoring cannot guarantee zero latency or safe speaker feedback.

Own code is MIT. Study Sonusmix’s MPL policy before duplicating it. BlackHole is GPLv3: evaluate an external installation, but do not silently vendor it. Windows capture, sample drivers and signed release labels each need transport and certification proof.
